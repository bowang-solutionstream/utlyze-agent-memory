# I2E v2 — proposed entrypoint

This is proposed future skill text for independent review. Do not activate it, dispatch its roles, mutate the live skill, or interpret it as permission to execute a workflow during this review. [PROPOSAL.md](PROPOSAL.md) is the consolidated design contract and records initial proposed positions and deferred owner decisions. V6 was independently approved at design level. V7 introduces separate High/Medium/Low severity and priority, High-triggered Astra ownership and deferred Low observations. It requires its own independent verdict and does not activate policy.

## Intended use after adoption

Use for an authorized engineering task or a small coherent batch in one project. Preserve read-only/review requests and explicitly selected legacy profiles. Establish allowed actions from actual user/project authority; approvals do not grant new release authority.

The tech lead scopes and plans but never implements. One project manager coordinates. Implementation belongs to separate workers. Independent reviewers are eligible by actual session/contributor history, not role labels. Ordinary checks and bookkeeping should run in code.

## Routing

Requested settings: Astra / max / Standard; Sol and Terra / max / Fast. Luna is excluded. Record requested settings separately from host/adapter-attested effective model/effort/tier and session/context provenance. Unknown or unsupported settings hold dispatch; prompt labels and self-reports are insufficient. Unsupported routing does not become valid because the prompt names the desired model.

Use High / Medium / Low for finding severity and, separately, task priority. Apply PROPOSAL §3: High priority **or** a High finding affecting the work **or** Critical technical risk routes manager, planning-only lead and implementation ownership to separate Astra roles; approved bounded Sol parts remain possible. With no higher trigger, Medium uses Sol manager/lead and a separate Sol worker by default, with Terra for explicitly planned bounded routine edits. Explicitly requested Low-priority work remains in scope: Sol coordinates/plans, Terra implements bounded routine edits and Sol handles the rest. Incidental Low findings receive DEFERRED_LOW observations and no automatic dispatch. Low-priority work with a High finding follows the High route.

Keep difficulty and technical risk separate. Critical is a risk/escalation trigger, not a fourth severity; difficult architecture still requires the applicable Astra challenge. Classify before filtering/dispatch and reassess on new evidence. No findings is NOT_APPLICABLE; unknown required classification holds dependent dispatch while allowed read-only diagnosis can continue. Do not classify uncertain material harm as Low. Route changes require current exact-plan approval and retain prior obligations; historical receipts are not relabeled. Baseline groundwork preserves installed routing until adoption.

Every exact task or batch plan needs fresh independent Astra approval. All seven final triggers must be explicitly assessed and reassessed. Astra implementation ownership does not replace independent Sol assurance/rechecks or itself determine final-review requirements. Finding severity and priority do not establish technical-risk eligibility for reduced assurance.

## Lifecycle spine

1. **Intake:** identify project/client/repo, instructions, current worktree, objective, owned paths, allowed actions and observable acceptance. Retrieve applicable decisions/canonical cases. Unknown routing inputs and unavailable required stores are explicit gaps.
2. **Plan:** the tech lead decomposes the request into bounded tickets and must assign multi-ticket work to batches of at most five ticketed changes. Produce a proportionate immutable contract with per-ticket acceptance, repository/main branch, issue IDs, batch/dependency/commit mappings, scope/exclusions, risk, verification obligations and triggers. Use one worker unless parallel isolation is beneficial.
3. **Challenge and approve:** the manager obtains fresh Astra exact-plan approval and applicable independent decision challenges. Preparation may be shared, but each mapped decision retains its identity and verdict; plan approval cannot silently close an unresolved architecture question. Preserve rejections and unresolved findings. A mapped meaningful RED may challenge an ordinary behavioral claim. Three unresolved substantive cycles of the same decision stop dependent work.
4. **Dispatch:** start only with the current approved plan, completed dependencies, compatible package ownership and confirmed invocation settings. Default to isolated per-attempt writable outputs with validated isolation from other attempts, integration destinations and immutable artifacts. Shared-worktree replacement requires confirmed full-writer quiescence/write revocation and reconciled source identity; otherwise HOLD (PROPOSAL §9.1). Preserve source/write boundaries and actual identities.
5. **Implement with evidence:** inspect each real preflight before its dependent action. VERIFY has no source writes and collects applicable CHECK evidence. TEST_ONLY edits only approved test scope and preserves production bytes. Behavioral work requires meaningful assertion RED, then authorized PRODUCTION and unchanged-test GREEN. Justified nonbehavior work uses applicable proof; no behavioral waiver is assumed. Preserve focused ticket-linked commits as code/diff/recovery traces; their existence alone does not trigger a full independent audit per commit.
6. **Integrate:** capture stable outputs into controlled immutable artifacts, stage privately and admit only under current fencing tokens/dependency versions using the expected ledger sequence. A token/sequence change rejects admission; stale writes cannot enter a replacement or acceptance candidate. Record output provenance and actual candidate/base/harness/configuration, then run required deterministic and cross-task checks. Integration edits invalidate affected proof (PROPOSAL §9.1).
7. **Verify independently:** fully eligible Low-risk work uses the proposed one-fresh-Sol route. Medium/High technical risk and ineligible/unknown routes retain baseline assurance; defer any intermediate route until evidence and owner selection support it. Required baseline code/security/test audits use three distinct eligible Sol sessions. Use targeted independent execution and source/assertion review; distinguish executed from inspected evidence. Report High/Medium findings under §6 and keep incidental Low observations outside routine findings.
8. **Complete obligations:** run required non-final specialists, resolve findings with current evidence, consult final canonical cases and run applicable regressions. A required fresh Astra final review follows these results and excludes prior participants. Avoid duplicate specialist sessions when one eligible audit demonstrably covers the same obligation.
9. **Gate and deliver:** check current candidate/plan/profile/harness identity, reviewer eligibility, all findings, mandatory proof/approvals and exact action authority. The adapter must enforce relevant expected source/target/artifact identities at the external operation and verify the resulting identity/relation (PROPOSAL §9.2). Changed preconditions reject or require renewed validation before effect; unsupported guarantees HOLD the action. Record actual commit/PR/CI/merge/deploy results separately.
10. **Report and learn:** establish technical readiness before marking completion. Return actual status and a concise factual engineering brief, record its links and finish consistency checks. Capture observed maintainability patterns and evaluated lesson dispositions through §11.1; passing tests need not hide unnecessary complexity, and an uneventful run need not invent observations. Preserve continuation work after interruption; no fabricated success, alternatives or learner assessment.

## Mandatory ticket batches and Git workflow

If the lead decomposes a request into multiple tickets, review batching is required. Each batch has at most five bounded ticketed changes. Count tickets/logical scope, not files, commits or PRs; do not hide extra scope under a renamed umbrella ticket. Code validates declared membership/count/mappings; independent scope review checks the actual diff and original intent for hidden independent changes. A single-ticket request or remainder may be smaller, and no batch waits to reach five. Group compatible sibling tickets; any dependency/access/release/rollback reason for separate groups or a singleton is recorded in the existing approved plan. Requests larger than five are partitioned with explicit dependencies and parent completion tracking.

Every batch preserves per-ticket acceptance, ownership, focused tests and applicable RED/GREEN. Integrate under §9.1, then verify the complete candidate and interactions with the selected independent assurance route; mandatory specialists remain. Commit checkpoints do not require repeated full independent audits. Failed tickets hold the batch. Any changed membership/scope receives renewed exact-plan approval and current proof; retain task/finding/repair history, continuation and coherent rollback. A/B acceptance cannot complete the parent A/B/C request.

Use each project’s identified GitHub code repository for Issues and PRs, reusing an existing repo where appropriate. Record the exact repository/default target (`main` by convention), actors and authority at intake. A portfolio board may aggregate projects; it does not relocate code PRs. Repository creation/remote writes are separate authorized actions, and a local-only request stays local-only.

The authorized trace is parent issue → bounded tickets → approved batches → isolated worker commits → combined candidate/diff → **one batch PR to main** → current independent review/CI evidence → conditional authorized merge → actual issue dispositions. Draft PRs may be opened early when permitted. Baseline audit counts remain unchanged where required. Local-only dependent batches may consume immutable, technically accepted predecessors with pinned acceptance/dependency identity and separate base/delta/proof for their own at-most-five new ticketed changes. The full source and inherited obligations remain visible; reject unaccepted, changed or superseded dependency proof. Local acceptance never means merged/delivered. For later GitHub delivery, merge predecessors first, reconcile the dependent branch against the actual target and renew affected proof/approvals; its PR diff cannot include uncounted unmerged tickets. Stacked-PR automation is deferred.

Apply PROPOSAL §8.2 for commit/issue/PR/SHA mapping, current proof, squash trace retention and accurate issue closure. Preserve original commit objects/diffs through durable refs or verified archives before squash/history/checkout cleanup. A Git log is not a verification receipt. Keep raw execution/failure evidence in the existing ledger/artifact store, linked to the candidate and PR. Merge only through §9.2’s operation-enforced expected identities; read back the resulting SHA. Unfinished parent, deployment or acceptance obligations stay open.

## Failure, findings and recovery

Capture every real failure before repair with broken source/evidence and a stable defect linked through the existing canonical helper/schema. Consult scoped cases before each repair; preserve known digests, capture/lookup gaps and prior attempts. Two failed repairs of one defect require Astra diagnosis before another attempt. Expected RED is separate.

Routine findings use only High (serious impact) or Medium (material, bounded impact), with stable ID, requirement/risk, evidence, consequence, smallest correction and validation. Apply the full impact definitions in PROPOSAL §6. Precise static/security evidence may block without unsafe execution. Classify before suppression: uncertain material risk needs investigation, and a preference cannot be inflated to Medium to evade the filter. Resolve supported disagreements explicitly; no-findings is valid.

Retain encountered Low findings as compact, deduplicated DEFERRED_LOW entries in existing observation/decision artifacts: ID/key, source/candidate location, reason for Low and revisit trigger. Omit their details from routine review output. Add no backlog/store, automatic ticket, repair/re-review, owner/due-date chase, capture quota or scheduled sweep. New evidence, repeated aggregate burden, changed requirements or a user request can prompt reassessment; preserve the original entry and link any supported Medium/High reclassification before current planning/routing and repair. DEFERRED_LOW means deferred, not FIXED or risk-accepted, and needs no independent recheck solely for deferral.

The Low filter cannot hide failing acceptance checks, real failure capture, security obligations, user-requested work or prior actionable findings; these keep their existing evidence/disposition requirements. Preserve baseline FIXED-finding recheck independence: the required Sol recheck reviewer is distinct from contributors and the original finding reviewer. Primary verifier continuity does not waive that extra obligation. Several findings may share a recheck session only if it meets each finding’s independent eligibility rules; measure detection and delay before proposing relaxation. Human risk acceptance needs actual human evidence.

A relevant source, plan, base, instruction, profile, harness, dependency or configuration change invalidates affected proof/reviews. No retrospective authorization. VERIFY cannot close an open test/production cycle. Explicit approved bounded remediation repairs only its named obligations while retaining all other prerequisites.

On restart, reconcile sessions, claims, artifacts and action outcomes before redispatch. Reject stale claims/results and isolate their filesystem effects under §9.1. Reconcile external actions by both occurrence and resulting source/target/artifact identity under §9.2: only intended confirmed success is delivered; confirmed unintended effect enters failure/incident handling; unknown outcome remains HOLD. An idempotency key does not enforce target freshness. Any retry requires current authority/preconditions; do not blindly repeat. Record corrections/withdrawals/supersession append-only. Unknown evidence never becomes a successful no-op.

## Maintainability learning

Apply [PROPOSAL §11.1](PROPOSAL.md#111-maintainability-observations-and-rule-evaluation) within existing planning, review and reporting. Link pattern evidence/scope, the smallest proposed response, evaluation and disposition in existing observation/decision artifacts; keep the canonical failure schema unchanged. Low observations follow §6 without automatic implementation, rule creation or re-review. Compare motivating and held-out cases, including legitimate-use counterexamples, before adopting a reusable rule change. Pending lesson evaluation alone does not block the original task; material findings remain governed by §6. Consolidation preserves applicable requirements; retirement needs obsolete-risk or replacement-control evidence and retained history. Obsolete guidance may leave the active set without a successor. Rule changes use existing independent review and actual change authority, preserve evidence invalidation and never waive §6. No new store, audit stage, observation quota or automatic rule activation is introduced.

## Assurance limits and adoption

Formal checking is selective: identify the property, assumptions/bounds, checker result and evidence linking model transitions to implementation. A sync commit or passing bounded model is not blanket implementation proof. Relevant changes require reassessment. Prioritize ownership/replacement, stale approval rejection and ambiguous publication recovery, including fairness/environment assumptions and reachable success paths. Trace agreement is partial evidence. No per-test mutation quota or universal 100% mutation target is imposed. Run mutation/fault probes on disposable copies; protect the frozen acceptance candidate. Same-candidate/setup evidence reuse is allowed; cross-candidate caching is deferred. Historical RED is provenance, not current acceptance proof.

No individual-run budget or budget-approval gate. Usage is optional measured telemetry; unknown is not zero. Local consistency checks do not authenticate models, enforce OS permissions, prove task correctness or grant release authority.

Use the smallest runtime extension: existing ledger, one deterministic reducer/policy evaluator, immutable evidence, task attempts/dependencies and one dispatch/action adapter boundary; derive batch readiness from obligations. After independent design approval and separate implementation authorization, implement/test those contracts while preserving baseline assurance. Before adoption-grade trials, freeze owner-selected severity-miss, unsupported-blocker, latency/intervention thresholds and workload/adjudication rules. Evaluate empirical improvements, reviewer reduction, batching, Low filtering and routing separately; freeze both arms’ verdicts before sharing findings/repair, use concealed seeded faults and adjudicated real defects, include failed attempts, deferred-record overhead and batch waiting, and report shadow costs separately. Relabeling/suppressing defects cannot improve measured quality. Obtain explicit owner selection before activating v2. Do not use this draft to certify old-profile completion or change installed defaults automatically.
