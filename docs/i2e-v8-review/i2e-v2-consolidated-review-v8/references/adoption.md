# Implementation and adoption

Status: proposed sequence. This document starts no implementation or trial.

## Small first build

1. Select and qualify the controller base. Preserve the installed, frozen, current-source, and isolated-repair identities. Correct completion/readiness and proof-coverage faults before trusting completion.
2. Implement the plan and policy fields needed by this contract. Keep the existing ledger, case schema, and CLI boundary. Test the actual phase and amendment rules.
3. Draft and exercise the included entrypoint and role prompts. A fresh session must identify its role, lane, and next action from the provided package.
4. Qualify one worker-write mode and one GitHub adapter. Add safe cleanup. Defer extra adapters, graph frameworks, and cross-candidate caching.
5. Obtain implementation review and select the exact profile before installation. Existing runs keep their recorded rules unless an explicit migration is approved.

The current source has useful light-route, command-receipt, and session-log work. It is not a drop-in v8 implementation. Its light route permits some Medium-risk work that Direct does not.

## Minimum probe set

| Probe | Required observation |
|---|---|
| Prompt forward exercise | Each role selects a lawful next step and reports limits without loading the entire history |
| Route examples | Urgent trivial work can be Direct; High technical risk selects Critical; unknown risk cannot authorize writes |
| High finding and handoff | Only affected repair ownership changes automatically; reassessment can change the lead/lane; history remains |
| File expansion | A file inside the approved surface can be added after impact checks; an excluded surface is blocked before write |
| Phase and coverage | Setup failure cannot count as RED; changed tests need a new cycle; an aggregate receipt missing an acceptance fails |
| Worker replacement | Old worker and child cannot change replacement/integration output; stale attempt admission and revocation during staging fail |
| Batch change | A delegated independent removal preserves continuation; prerequisite removal requires replanning |
| Source and target changes | Changed PR head or target rejects delivery or receives current combined validation before effect |
| Lost acknowledgment | Intended success, no effect, unintended effect, and unknown remain distinct |
| Cleanup | Pushed source with local ignored evidence is retained; fully preserved inactive work can be removed |
| Failure learning | Material first failures are captured; routine errors retain raw evidence; repeated failure promotes without losing history |
| Legitimate completion | A valid narrow repair and a clean Direct task can finish; guards do not disable the success path |

Use deterministic tests where possible. Inspect unsafe scenarios through precise source arguments if execution is inappropriate. Record tested bounds and limits.

Formal methods are optional and targeted. Use them when a consequential state property or recurring controller defect justifies the effort. Include reachable success, environment assumptions, and an implementation mapping. No universal formal gate or mutation quota is added.

## Exploratory trial

Start with a bounded non-P0 feasibility exercise. Keep current assurance and model routing fixed while testing stronger receipts and clearer prompts. A design review alone cannot pass this exercise.

After selecting the relevant proposed policy, use up to ten suitable real tasks for an exploratory comparison. A task is suitable only when its actual authority, risk, checks, and adapter capability qualify. No production-risk exception comes from the trial label.

Test Direct reviewer reduction separately from model-routing changes and batching. Use the same frozen candidate and acceptance when comparing the selected verifier with baseline shadow audits. Freeze verdicts before sharing findings or repairing the candidate.

Record one row per attempted task: lane, candidate, acceptance, sessions, wall-clock time, actual findings, later defects, interventions, and usage if available. Include failures, interruptions, repair work, and batch waiting. Separate shadow costs from the proposed steady-state route.

Specify unacceptable outcomes and stopping rules before the trial. A material missed defect or unsupported completion stops advancement of the affected route pending investigation. A small sample can expose faults and establish feasibility. It cannot estimate a reliable rare-defect miss rate or justify broad safety claims.

Adoption-grade evaluation retains owner-selected thresholds, representative workload, severity definitions, independent adjudication, and held-out cases. Do not change thresholds after seeing outcomes. The frozen empirical proposal remains a reference; it has not become active policy.

## Decisions and activation

The review can approve this as an implementation design. Activation separately requires:

- An exact implementation and compatible record schema.
- Current tests and independent implementation assurance.
- Qualified host settings and worker/delivery capabilities.
- An explicit selection of `tier_policy`.
- Approved trial scope and adoption evidence appropriate to the intended use.
- Owner selection of the profile and a recovery path.

V8 proposes the lane, routing, write-boundary, failure-record, and delegated-removal changes as one coherent candidate. Publishing this candidate does not select them operationally.

Keep max effort, distinct finding rechecks, and the at-most-five-ticket cap. Lower effort, original-finder closure, broader Direct eligibility, and general cross-candidate reuse remain deferred.

No live skill, model configuration, repository setting, or canonical record changes merely because the proposal or its independent review is published.
